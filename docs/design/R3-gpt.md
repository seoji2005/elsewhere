가정: 아래 금액·확률·작업 시간은 이번 라운드의 **조정 가능한 설계값**이다. 방향은 [GDD 합본](/home/dev/game/docs/design/GDD.md)을 따른다. 화폐는 정수 ‘결’, 시간은 게임 내 분이며, 실제 플레이 시간과 구분한다. 계약·직원 정책을 읽는 동안에는 시간이 멈춘다.

현재 코드에는 `TycoonSystem` 등록부와 AI 계약의 데이터 사용 조항이 아직 없다. 따라서 아래 파일 구조와 확장 지점은 구현 제안이다. 파일 수정과 테스트 실행은 하지 않았다.

**A. 두 번째 사업 — 주문 누락을 줄이는 AI 업무 자동화 외주, C103·C104**

**1. 플레이어가 파는 것은 ‘자동화 범위와 책임의 약속’이다.** 첫 고객은 가게에 자주 오는 작은 배달 사업자다. 주문을 메시지로 받다가 변경 사항이나 주소를 빠뜨리는 문제가 있다. 플레이어는 개발자 NPC와 고객 사이에서 처리 규칙을 합의하고, 실제 사례로 결과를 검수한다. 프로그램을 직접 작성하거나 모델 성능 수치를 올리는 조작은 없다. 중요한 질문은 “이 주문을 자동으로 확정해도 되는가”, “여기서는 누구의 확인을 기다려야 하는가”다.

소매에서는 이미 정해진 상품을 누구에게 얼마에 팔고 언제 진열할지 판단한다. 이 사업에서는 아직 명확하지 않은 요구를 약속으로 바꾸고, 자동화가 넘어서는 안 될 경계를 정한다. 고객의 “다 알아서 해 주세요”를 그대로 받아들이면 개발 범위와 책임이 커진다. 반대로 모든 주문을 사람이 확인하도록 하면 안전하게 시작하지만 고객이 절약하는 시간이 작다. 이 차이를 가격·납기·검수 사례에 함께 반영한다.

**2. 첫 기회는 실제 문제 기록에서 나온다.** 고객 NPC가 운영하는 사업에는 `missingOrder`, `duplicateOrder`, `changedOrder` 같은 업무 기록이 있다. 최근 3일 안에 누락 기록이 하나 이상 있고, 해당 NPC가 플레이어 가게에서 구매를 마친 뒤 고민을 이야기하면 기회를 인지한다. 단골 여부는 기존 `promotePersona`처럼 완료 방문 3회 이상을 사용한다. 다만 단골이라는 이유만으로 사업자 직업이나 누락 사건을 새로 만들지는 않는다.

공개 문의도 처음부터 가능하다. 업무 탭에서 ‘다른 사업 알아보기 → 반복 업무 도와주기’를 누르면 같은 실제 문제를 가진 사업자가 응답한다. 단골 경로는 고객의 주문 습관과 사례 두 개를 미리 알고 시작한다. 공개 문의 경로는 질문 두 개로 같은 정보를 얻는다. 잔액이나 직원 보유 여부는 문의 조건이 아니다. C097 의존성은 시제품 제작 순서이며, 세계 안의 산업 해금 조건으로 쓰지 않는다.

**3. 고객과 처음 합의할 목표는 하나다.** “받은 주문이 목록에서 사라지지 않고, 확인이 필요한 주문은 따로 모인다.” 매출 증가, 배송 최적화, 재고 예측은 첫 계약에서 제외한다. 주문 입력은 게임 안에 존재하는 메시지 기록이며 실제 외부 AI 서비스에 보내지 않는다. 고객은 하루 대표 주문 묶음과 누락 사례를 제공한다. 플레이어가 질문을 마치면 요구사항 초안이 생성되고, 고객이 확인해야 계약 초안으로 바뀐다.

초안에는 입력 경로, 처리 결과, 사람이 맡는 예외, 담당자, 응답 시한을 적는다. 예를 들어 “메시지 주문을 목록으로 정리한다. 주소가 없으면 자동 확정하지 않는다. 고객 사업자가 확인 대기 목록을 30분마다 처리한다.”라고 표시한다. 사람이 확인할 담당자가 없으면 자동화 범위를 넓혀 해결할 수 없다. 담당자를 지정하거나 확인이 필요한 업무의 처리 시간을 다시 합의해야 한다.

**4. 협력자는 두 명 중 고르되 실제 일정으로 움직인다.**

| 후보 | 가능한 작업 | 첫 계약 작업 시간 | 기본 개발비 | 지급 조건 |
|---|---|---:|---:|---|
| 꼼꼼한 입문 개발자 | 목록 정리, 정상 주문 자동 등록 | 60 / 90분 | 80 / 120결 | 착수 때 절반, 납품 때 절반 |
| 업무 경험이 있는 개발자 | 위 작업 + 중복·변경 자동 반영 | 45 / 60 / 90분 | 110 / 150 / 180결 | 착수 때 절반, 납품 때 절반 |

카드에는 얼굴, 지금 가능한 시간, 처리해 본 사례, 지원하는 범위가 먼저 나온다. 능력 종합 점수로 고르게 하지 않는다. 입문 개발자에게 변경 자동 반영을 요청하면 “원래 주문과 연결하는 부분은 아직 못 맡아요”라고 답한다. 지원하지 않는 기능을 돈으로 즉시 해금할 수 없다. 후보의 작업 시간은 실제 일정에 예약하며, 같은 시간에 다른 프로젝트도 진행하는 중복 배정을 금지한다.

선금 없는 길은 입문 개발자의 ‘첫 실적 공동 제작’ 제안이다. 목록 정리 범위만 가능하고, 고객에게서 실제 대금을 받으면 개발자에게 120결을 지급한다. 실패하면 개발자는 보수를 받지 못한다는 조건을 미리 수락한다. 이 선택에는 현금이나 친밀도 하한이 없지만, 개발자가 해당 제안을 받아들일 일정과 의사가 있어야 한다. 첫 시제품의 새 세계에는 이 조건을 가진 후보 한 명을 배치한다.

**5. 범위 선택은 세 가지이고, 사람이 확인할 부분이 항상 보인다.**

| 범위 | 자동 처리 | 사람이 확인 | 대표 10건의 확인 시간 | 계약 총액 |
|---|---|---|---:|---:|
| 목록 정리 | 모든 주문을 확인 목록에 모음 | 모든 주문의 최종 확정 | 30분 | 180결 |
| 정상 주문 처리 | 필수 정보가 완성된 새 주문 등록 | 정보 누락·중복·변경 | 18분 | 260결 |
| 중복·변경까지 처리 | 정상 주문, 정확한 중복 제거, 식별 가능한 변경 반영 | 정보 누락·식별 불가·충돌 | 6분 | 340결 |

대표 묶음은 정상 주문 4건, 필수 정보 누락 2건, 정확한 중복 2건, 원래 주문이 식별되는 변경 2건이다. 수작업 기준은 건당 5분, 총 50분이다. 따라서 예상 절약 시간은 각각 20·32·44분이다. 자동 처리에는 사람 확인 시간을 0분, 확인 목록 처리에는 건당 3분을 적용한다. 이는 이 표본의 예상치이며 실제 하루 절약 시간이라고 표시하지 않는다.

어떤 범위에서도 없는 주소를 만들어 넣거나, 연결할 주문이 불명확한 변경을 추측해서 확정하지 않는다. 환불·결제·배송 출발 지시는 첫 계약에 포함하지 않는다. 범위를 넓히면 처리 가능한 사례가 늘지만 검증해야 하는 기능도 늘어난다. 플레이어는 선택 직후 “자동 처리 4건 / 사람 확인 6건”처럼 결과를 보고, 사례를 눌러 왜 해당 쪽으로 분류되는지 확인할 수 있다.

**6. 계약에는 돈과 데이터 약속을 같은 중요도로 적는다.** 필수 항목은 고객 계정, 수취 계정, 개발자 계정, 범위 버전, 가격, 선금, 작업 가능 시간, 검수 사례, 재작업 횟수, 실패 정산, 데이터 조항이다. 개인으로 계약해도 되고 이미 보유한 법인으로 계약해도 된다. 법인이 없다면 개인 계약이 기본값이다. 새로운 법인 계정을 만들더라도 잔액은 0이며, 기존 계정에서 실제 출자한 금액만 들어간다.

데이터 조항은 사용 목적, 개발자가 볼 필드, 보관 기간, 다른 프로젝트 재사용 여부로 구성한다. 기본안은 주문 식별자·상품·수량만 개발자에게 제공하고, 주소와 연락처는 고객 화면에 남긴다. 개발자는 가명 처리된 시험 자료를 사용하며 납품 후 7일에 작업 사본을 삭제한다. “향후 다른 고객의 서비스 개선에도 사용할 수 있다”는 제안이 있으면 고객의 별도 동의가 필요하다. 동의하지 않은 데이터 사용은 실행할 수 없다.

**7. 변호사는 원문을 여는 열쇠가 아니라 의미를 설명하는 전문가다.** 원문은 처음부터 모두 읽을 수 있다. 플레이어가 직접 “다른 고객에게도 사용”을 찾아 삭제 요청해도 된다. 변호사는 “이 문장은 이번 주문 정리뿐 아니라 다른 프로젝트에도 자료를 쓰겠다는 뜻”이라고 설명하고, 의뢰 범위에 맞는 수정안을 제공한다. 검토 결과가 비어 있어도 “문제 없음”으로 단정하지 않고 “이번 검토에서 확인한 항목 없음”으로 표현한다.

현재 `advisors.ts`와 데이터에는 AI 계약·데이터 조항이 없으며, 일반 검토는 1~5일이다. C101에 **데이터 조항 한 건 검토**를 추가하는 것이 이 명세의 제안이다. 비용 30결, 작업 시간 15분, 목적·보관·재사용 세 항목만 검토한다. 일반 계약 검토의 등급과 소요 시간은 바꾸지 않는다. 고객이 비용을 부담하기로 합의했다면 고객 지갑에서 변호사 계정으로 직접 지급하고, 아니면 의뢰자가 지급한다.

같은 계약 버전과 자료로 다시 상담해도 결과는 동일하다. 기존 `reviewContract`가 받는 표본 함수는 계약·검토 항목에 연결된 `tycoonCore.roll`로 공급한다. 새 상담 명령 ID를 난수 키로 쓰지 않는다. 수정안 채택은 별도 명령이며 고객과 개발자가 모두 동의한 뒤 계약 버전을 올린다. 검토받았다는 사실만으로 원문이나 실제 데이터 권한이 자동 변경되지는 않는다.

**8. 일반 계약은 40% 선금, 성공 뒤 60% 잔금이다.** 목록 정리 180결을 입문 개발자와 계약한 경우, 고객이 플레이어에게 72결을 지급하고 플레이어가 개발자에게 착수비 40결을 지급한다. 성공하면 고객이 플레이어에게 108결을 지급하고, 플레이어가 개발자에게 남은 40결을 지급한다. 변호사 비용을 제외한 플레이어 몫은 100결이다. 모든 금액은 고객·플레이어·개발자의 실제 계정 사이에서 이동한다.

계약 서명과 실제 착수는 구분한다. 선금 계약의 착수 명령은 고객→플레이어 선금과 플레이어→개발자 착수비를 순서대로 넣은 `settle` 묶음이다. 어느 지급이라도 불가능하면 둘 다 취소하고 `awaitingFunding`에 남는다. 선금 없는 공동 제작은 지급 없이 작업 예약만 확정한다. 성공 때 고객→플레이어 180결, 플레이어→개발자 120결을 하나의 묶음으로 처리하므로 플레이어 잔액이 0이어도 시작하고 정산할 수 있다.

**9. 개발은 기다리는 막대보다 확인할 일이 있는 짧은 과정이다.** 개발자는 예약된 근무 분에만 진행도를 올린다. 50% 지점에서 대표 사례 하나를 보내고 “이 주문은 사람이 확인하는 게 맞나요?”라고 묻는다. 답은 기존 합의의 재확인이다. 합의를 바꾸면 새 버전의 가격·남은 시간이 표시되고 양측 동의를 받아야 한다. 같은 범위를 다시 선택해 진행도나 실패 가능성을 초기화할 수 없다.

게임 속 개발 결과는 서버에서 코드를 생성하는 방식이 아니라, 범위별 처리기와 결함 상태를 가진 결정론적 시뮬레이션이다. 지원하는 기능군마다 착수 때 결함 여부를 한 번 결정한다. 입문 개발자 8%, 경험 개발자 3%를 초기값으로 두고 `roll(seed, 'ai:defect', contractId + featureId, 0)`를 사용한다. 결함이 있어도 검수 전에 실제 고객 주문을 변경하지 않는다. 동일한 결과물에는 언제나 동일한 검수 결과가 나온다.

**10. 검수는 정답 맞히기보다 약속과 결과를 비교하는 과정이다.** 대표 10건 외에 주소 누락, 같은 요청 재전송, 권한 없는 데이터 재사용을 검사하는 안전 사례를 둔다. 각 사례는 입력, 기대 처리, 실제 처리, 사람 확인 여부를 보여 준다. 정상 주문 사례만 잘 처리해도 통과하는 평균 점수 방식은 쓰지 않는다. 합의한 기능과 안전 조건을 모두 만족해야 한다. 단순 범위에서 모든 주문을 확인 목록으로 보낸 것은 정상 결과다.

플레이어는 실패 사례를 열어 “이 경우는 자동 확정하면 안 된다” 또는 “같은 주문이 두 번 생기면 안 된다”를 선택한다. 실패한 기능군 전체를 수정 대상으로 지정할 수 있다. 재작업은 한 번 포함되며 30 작업 분이 걸린다. 지정한 결함을 수정하고 기존 시험 전체를 다시 실행한다. 무관한 항목만 수정하거나 해결되지 않은 실패가 남으면 최종 실패다. 동일 시험을 반복 실행하는 것은 재작업으로 세지 않으며 결과도 달라지지 않는다.

**11. 통과·재작업·실패는 서로 다른 정산을 만든다.** 통과하면 결과물 버전이 고정되고 잔금 청구가 생성된다. 재작업 상태에서는 잔금을 청구하지 않는다. 최종 실패 또는 합의된 납기 초과 시 고객은 종료하거나 새 납기를 협의한다. 자동 연장하지 않는다. 일반 계약에서 이미 지급한 개발자 착수비는 수행한 작업 대가로 남고, 고객 선금에서 그 금액을 뺀 나머지가 환급 대상이다. 이 조건은 서명 전에 숫자로 표시한다.

180결 예시에서는 실패 시 환급액이 32결이다. 플레이어가 이를 이미 다른 곳에 사용했다면 가진 만큼 실제 반환하고 나머지는 환급 채무로 남긴다. 잔액을 음수로 만들거나 부족분을 생성하지 않는다. 선금 없는 성공보수 계약은 실패 시 고객 청구액과 개발자 보수 모두 0이다. 변호사 검토처럼 이미 제공된 별도 서비스의 비용은 되돌리지 않는다. 실패 원인은 ‘개발 결함’, ‘고객 자료 미제공’, ‘범위 변경 미합의’로 기록한다.

**12. 잔금 미납은 기술적 실패와 구별한다.** 고객 지갑에 잔금이 없으면 검수 통과 기록은 유지하고 `awaitingPayment`에 머문다. 사용권은 아직 활성화하지 않으며 플레이어와 개발자에게 성공 매출을 적립하지 않는다. 다음 날 실제 지급을 재시도하거나, 고객과 새 지급일을 합의할 수 있다. 지급이 성공해야 납품 완료가 된다. 고객이 주문 처리로 절약한 시간이 곧바로 새 화폐나 매출로 전환되는 규칙은 없다.

납품 후에는 실제 주문 묶음의 자동 처리 건수와 사람 확인 시간을 기록한다. 고객이 확인 대기 목록을 방치하면 누락이 아니라 ‘확인 지연’으로 표시한다. 첫 운영 묶음에서 변경 주문 확인이 반복되면 “변경까지 맡길 수 있을까요?”가 다음 일감 후보가 된다. 후속 기회는 새 계약이며 자동 반복 수입이 아니다. 기존 개발자 일정, 고객의 필요, 동의된 데이터 사용 범위를 다시 확인한다.

**13. 폰에서는 한 계약 안에서 끝낸다.** 업무 탭의 고객 메시지에서 계약 상세를 열고, ‘문제 확인 → 협력자 → 처리 범위 → 계약 → 시험 결과’ 순으로 내려간다. 하단에는 현재 필요한 행동 하나를 고정한다. 범위 화면은 자동 처리와 사람 확인을 두 묶음으로 보여 주고, 예상 절약 시간과 총액을 바로 갱신한다. 계약 원문과 변호사 설명은 같은 화면에서 펼친다. 다른 앱을 다녀오도록 요구하지 않는다.

실제 체험 목표는 문제 확인 40초, 협력자·범위 선택 70초, 계약·데이터 검토 70초, 중간 확인 30초, 검수·수정 70초, 정산·다음 문의 30초로 약 5분 10초다. 작업 대기는 ‘다음 일까지 넘기기’로 이동할 수 있지만 배송·임금·직원 근무는 건너뛴 모든 분에 처리한다. 긴 글을 읽느라 시간을 소비하지 않도록 기본 화면은 요약만 보이고 원문은 펼치도록 한다.

예를 들어 플레이어는 공연에 가기 전 선금 없는 목록 정리 계약을 잡는다. 직원이 가게를 운영하는 동안 개발자는 시험물을 만든다. 공연 후 주소 없는 주문이 ‘확인 필요’에 남는 것을 보고 통과시킨다. 고객이 180결을 지급하고 개발자에게 120결이 이동한다. 고객은 “목록에서 빠지는 일은 없어졌어요. 다음엔 정상 주문까지 맡길까요?”라고 말한다. 첫 가게와 다른 사업을 시작했다는 감각은 이 판단과 대금 흐름에서 나온다.

**B. 첫 직원 위임 — 정책을 정하면 사장이 없어도 돌아가는 가게, C097**

**1. 첫 직원의 성공은 사장에게 돌아오는 질문이 줄어드는 것이다.** 채용 직후에도 정해진 가격으로 계산하고, 창고 물건을 진열하고, 예약 물건을 보관하는 정상 업무는 혼자 처리한다. 사장이 곁에 있어야 능력이 발휘되는 보너스는 두지 않는다. 직원이 숙련되면 같은 일을 사장보다 빨리 하고 실수도 적게 한다. 플레이어에게 남는 일은 모든 거래의 승인 대신 예산과 권한, 새 사업과 약속을 결정하는 것이다.

첫 체험의 목표는 8~14분 구간에서 시험 근무와 채용을 마치고, 그 뒤 사장이 다른 장소에 다녀와도 판매가 이어지는 것을 확인하는 데 있다. 일부러 지각이나 사고를 발생시켜 직원의 존재감을 만들지 않는다. 잘 맞는 정책과 충분한 재고가 있으면 아무 요청도 오지 않는 근무가 정상이다. 이후 문제는 정책 범위를 벗어난 주문이나 실제 공급 가격 변화처럼 설명 가능한 이유에서 생긴다.

**2. 지원자는 기존 주민이며 시험 근무도 유급이다.** 업무 탭에서 구인 문의를 열면 현재 일할 수 있는 주민 두 명의 카드가 나온다. 카드에는 가능한 시간, 희망 시급, 손·눈·말·성실의 관찰 정보, 성격 한 줄을 표시한다. 능력은 주민 ID에 연결해 저장하며 지원서를 다시 열어 바뀌지 않는다. 처음에는 ‘계산 경험 적음’, ‘수량 확인 꼼꼼함’처럼 설명하고, 시험 근무 뒤 실제 처리 속도와 오류 기록을 추가한다.

시제품의 시험 근무는 게임 60분, 시급은 후보에 따라 12·15결이다. 시험 근무에 동의하면 해당 한 시간의 임금을 가게 계정에서 직원 개인 지갑으로 먼저 지급한다. 지급 불가능하면 돈을 요구하며 메뉴를 숨기는 대신 예약 가능한 다른 시간을 보여 준다. 정상 채용 뒤에는 실제 유급 근무 분을 누적하고 퇴근 때 지급한다. 기존 고용 시스템과 연결하되 같은 근무에 급여를 두 번 계산하지 않는다.

**3. 시험은 실수 유발 시험이 아니라 일하는 방식 관찰이다.** 첫 60분에는 기존 구매 의도와 현재 재고로 일을 배정한다. 손님을 새로 생성하거나 구매력을 추가하지 않는다. 손님이 없으면 진열 가능한 재고를 정리한다. 두 업무 모두 없으면 ‘관찰할 업무 없음’으로 표시하며 합격·불합격을 자동 판정하지 않는다. 플레이어는 실제 기록을 보고 채용하거나, 다른 날 다시 제안하거나, 이번에는 종료할 수 있다.

채용은 시험 종료 화면에서 근무 시간·시급·정책을 확인하는 한 번의 결정이다. 시험 때 얻은 경험과 관계는 채용하지 않아도 주민에게 남는다. 첫 채용 직원에는 `firstHire` 표식을 붙이지만 특별한 실패 방지나 강제 이직 사건은 주지 않는다. 자회사 대표나 독립 서사는 이후 카드의 일이다. C097은 첫 고용 관계와 위임 경험이 자연스럽게 남을 만큼만 기록한다.

**4. 정책은 다섯 개로 제한한다.**

| 정책 | 선택값 | 처음 제안하는 값 |
|---|---|---|
| 하루 재량 지출 예산 | 0·40·80·120결 또는 정수 입력 | 80결 |
| 예약 손님 우선 | 도착 순서 / 약속 시각이 된 예약 우선 | 약속 시각 우선 |
| 할인 권한 | 할인 없음 / 최대 5% / 최대 10% | 최대 5% |
| 발주 승인 한도 | 건당 0·20·40결 또는 정수 입력 | 20결 |
| 계산·진열 우선순위 | 계산 우선 / 균형 / 진열 우선 | 균형 |

처음에는 추천값을 한 번에 적용하고 원하는 항목만 바꿀 수 있다. 하루 예산은 직원이 새로 결정하는 발주·배달비 같은 재량 지출에 적용한다. 이미 계약된 임금·임대료는 별도 의무라서 이 예산에 포함하지 않는다. 할인은 지출로 중복 계산하지 않고 매출 감소로 기록한다. 화면에는 “오늘 새 발주에 쓸 수 있는 돈”이라는 설명과 현재 지갑에서 기존 지급 의무를 뺀 가용액을 함께 보여 준다.

**5. 발주는 두 한도와 실제 잔액을 모두 통과해야 한다.** 직원이 18결짜리 보충 주문을 제안할 때 건당 한도 20결, 남은 하루 예산 50결, 실제 가용액 30결이면 즉시 실행한다. 같은 조건에서 주문이 24결이면 건당 한도를 넘으므로 요청한다. 18결 주문을 여러 개로 쪼개 우회하지 못하도록 한 번의 재고 보충 판단에서 나온 주문은 공급처·판단 ID별 총액으로 검사한다.

예산 사용액에는 실제 지급한 금액과 승인 후 아직 지급하지 않은 확정 발주액을 함께 포함한다. 취소가 확정된 발주는 미지급 약속을 해제하고, 실제 환급을 받은 경우에만 지급한 예산을 복원한다. 새로운 날의 예산은 초기화하되 미이행 약속은 지갑의 가용액 계산에 계속 남는다. 정책을 낮춰도 이미 체결한 주문을 몰래 취소하지 않는다. 화면에 “기존 발주 18결은 그대로 도착 예정”이라고 표시한다.

**6. 예약 우선은 재고 소유와 줄 순서를 분리한다.** 예약으로 확보한 물건은 어느 정책에서도 일반 손님에게 팔지 않는다. ‘도착 순서’는 대기열 순서를 지킨다. ‘약속 시각 우선’은 예약 시각 전후 10분 안에 도착한 예약 손님을 다음 계산 순서로 올린다. 이미 계산 중인 손님은 중단하지 않는다. 예약 수량 변경이나 물건 대체는 기존 약속 변경이므로 별도 권한이 없는 첫 직원은 사장에게 요청한다.

할인은 현재 표시 가격에서 권한 비율만큼 내릴 수 있고, 할인 후 단가가 매입 원가보다 낮아지는 거래는 자동 처리하지 않는다. 정수 화폐에서는 할인 후 가격을 올림한다. 직원이 흥정꾼에게 5% 할인으로 판매하려면 기존 구매 의도의 허용 가격과 실제 주민 지갑이 그 가격을 수용해야 한다. 할인 버튼을 누른다는 이유로 구매 성공을 보장하지 않는다. 판매와 재고 차감은 기존 구매 의도 ID로 한 번만 실행한다.

**7. 우선순위는 구체적인 작업 선택 규칙이다.** 직원은 동시에 계산 또는 진열 한 작업만 수행한다. 계산 우선은 대기 손님이 있으면 계산하고, 진열 우선은 당장 보충 가능한 빈 진열칸이 있으면 한 묶음을 먼저 보충한다. 균형은 대기 손님 2명 이상이면 계산, 그보다 적고 구매하려는 품목이 비어 있으면 진열을 선택한다. 둘 다 없으면 흐트러진 진열을 정리하고, 할 일이 없으면 쉰다.

모든 모드에서 가장 오래 기다린 손님이 인내 시간의 70%에 도달하면 다음 작업은 계산이다. 이는 숨은 예외가 아니라 정책 설명에 쓰는 공통 안전 규칙이다. 계산 중인 거래는 끝내고 전환한다. 진열은 한 묶음을 5개 이하로 제한해 긴 작업에 묶이지 않게 한다. 이미 예약되거나 다른 작업자가 잡은 상품은 작업 시작 시 확보하지 못하므로 중복 이동하지 않는다.

**8. 정책 밖 요청은 한 문제에 한 메시지만 보낸다.** 요청에는 무엇을 하려는지, 어떤 정책을 넘는지, 필요한 금액, 유효 시한, 답하지 않았을 때의 기본 행동을 넣는다. “발주해도 될까요?” 대신 “우유 4개 보충에 24결이 필요해요. 건당 한도 20결을 넘어요. 15분 안에 주문하면 오늘 도착합니다”라고 보낸다. 같은 부족 상태를 매분 다시 요청하지 않는다. 수량·가격·공급 조건이 달라졌을 때만 내용을 갱신한다.

플레이어의 선택은 ‘이번만 승인’, ‘정책 수정’, ‘거절’이다. 이번만 승인은 해당 요청 ID의 금액과 수량에만 유효하다. 승인 시점에 가격이나 재고가 바뀌었으면 재검사하고 바뀐 조건을 보여 준다. 미응답이면 발주하지 않고 가능한 다른 일을 한다. 할인 요청은 현재 권한 내 가격을 제안한 뒤 손님이 거절하면 거래가 끝난다. 한 손님의 미응답 때문에 가게 전체를 멈추지 않는다.

동시에 열린 요청은 같은 원인별로 합치고 최대 세 묶음만 전면에 보여 준다. 나머지는 숨겨서 소멸시키지 않고 업무 목록에 유지한다. 마감이 가까운 요청을 위에 놓으며 메시지 읽기는 시간을 멈춘다. 직원은 정책에 맞는 정상 거래를 보고하지 않는다. 직원에게 맡겼더니 메시지 처리량만 늘어나는 일을 막는 핵심 규칙이다.

**9. 경험은 실제 수행한 업무 시간에서 얻는다.** 손·눈·말은 각각 관련 작업을 수행한 분을 누적한다. 계산은 손과 눈, 수량 검사는 눈, 손님 응대는 말을 성장시킨다. 같은 작업 분이 관련 능력 둘에 기여할 수 있지만 한 능력의 경험을 중복 적립하지 않는다. 기다린 시간, 폰을 열어 멈춘 시간, 이미 완료된 거래를 다시 조회한 시간에는 경험이 생기지 않는다. 성실은 단순 반복으로 빠르게 오르는 생산 능력으로 취급하지 않는다.

각 능력의 유효 경험 시간을 `E`, 시작 능력을 `B`라 할 때 다음 곡선을 쓴다.

`능력 = min(95, B + 10 × min(1, E / 4) + 40 × (1 − exp(−E / 40)))`

첫 네 시간에는 가게에 익숙해지는 성장이 있고 이후는 완만해진다. 계산 작업량은 360, 분당 처리량은 `60 + 손`이다. 기준 사장의 손 능력을 60으로 두면 한 거래는 평균 3분이다. 손 42인 직원은 처음 약 3.53분, 관련 경험 4시간에는 약 3.11분, 12시간에는 약 2.94분, 40시간에는 약 2.62분이다. 숙련 직원이 사장보다 빨라지는 지점이 실제로 존재한다.

분 단위 처리에서는 매 거래 시간을 정수로 올림하지 않는다. `workRemaining`에서 매분 처리량을 차감하고 남은 처리량은 같은 분의 다음 가능한 작업에 사용할 수 있다. 그래야 3분과 2.9분의 차이가 장기 처리량에 반영된다. 다만 다음 작업도 재고·정책·손님 상태를 다시 검사한다. 빠른 직원이 한 분에 같은 손님에게 두 번 판매하는 오류를 허용하지 않는다.

**10. 지각은 드문 근무 시작 사건이다.** 시프트마다 한 번 다음 확률을 계산한다.

`p지각 = clamp(0.001 + 0.008 × (1 − 성실/100) + 0.012T + 0.010F + 0.008M, 0, 0.05)`

`T`는 실제 통근 경로 장애가 있으면 1, `F`는 직전 근무 과로가 있으면 1, `M`은 사기 40 미만이면 1이다. 성실 80에 원인 조건이 없으면 0.26%다. 비가 왔다는 이유만으로 모든 직원에게 가산하지 않는다. 그 직원이 이용하는 교통편의 지연이 있어야 한다. 지각 길이는 5~20분이고, 가능하면 시작 전에 연락한다. 늦은 시간은 유급 근무에 포함하지 않는다.

사기는 시작 60이며 근무 종료 때 갱신한다. 약속 임금 지급은 하루 +1, 미지급 상태는 하루 −5, 8시간 초과 근무는 초과 시간당 −2, 지킨 휴게 약속은 +1이다. 값은 0~100으로 제한한다. “급여를 지급했는데 잔액이 줄었다”와 “급여를 약속했지만 못 줬다”를 구별한다. 칭찬은 관계에 기록할 수 있지만 반복 누르기로 과로와 체불을 지우는 기능은 주지 않는다.

**11. 실수는 거래마다 낮은 확률로 생기되 안전 한도를 넘지 않는다.**

`p실수 = min(0.005, 0.0001 + 0.001 × (1 − 눈/100)² + 0.0015F + 0.001A)`

`F`는 과로 정도를 0~1로 환산한 값, `A`는 해당 작업의 상품 표기가 혼동 가능한 경우 1이다. 눈 60, 과로와 혼동이 없는 경우 작업당 0.026%다. 실수는 계산 전 수량 재확인으로 2분 더 걸리거나, 잘못 진열한 실제 상품을 다시 옮기는 결과로 시작한다. 첫 카드에서는 거스름돈 과지급까지 구현하지 않는다. 사라지는 돈이나 재고를 간편한 벌점으로 사용하지 않는다.

눈 능력이 오르면 오류가 줄지만 직원에게만 무작위 무능력을 부과하지 않는다. 사장 작업도 같은 작업 모델과 물리적 제약을 사용한다. 할인 한도, 발주 한도, 예약 재고 보호는 실수로 뚫리지 않는 권한 검사다. 직원의 능력은 실행 속도와 확인 오류에 영향을 주며, 사장이 정한 권한을 우연히 무시하는 근거가 되지 않는다. 실수 원인을 고치면 이후 확률도 실제로 내려가야 한다.

**12. 이직은 경고와 대안이 있는 장기 사건이다.** 사기 30 미만인 근무가 5회 연속이거나, 임금이 2일 이상 밀렸거나, 실제 라이벌 제안이 있을 때만 이직 의사를 검사한다. 그 외에는 확률 0이다. 조건 충족 뒤 하루 확률은 `min(0.05, 0.005 + 0.015L + 0.02W + 0.015R)`로 한다. `L·W·R`은 각각 장기 저사기, 체불, 유효한 라이벌 제안 여부다.

발생하면 최소 2일 뒤 퇴사 예정일을 알린다. 통보 즉시 직원이 사라지지 않는다. 라이벌 제안은 실제 자리와 지급 가능한 고용 조건이 있어야 유효하다. 임금 지급, 근무 시간 조정, 기존 제안보다 나은 조건처럼 원인에 대응하면 재고 요청을 받을 수 있다. 단순 대화 반복으로 확률을 다시 굴리지 않는다. 퇴사 후에도 같은 주민·경험·관계가 남으며 새 직장의 일정과 연결된다.

**13. 급여와 예산 부족은 자동으로 숨기지 않는다.** 정상 근무의 지급액은 `floor(누적 유급 분 × 시급 / 60)`에서 이미 지급한 금액을 뺀 값이다. 누적 계산을 사용해 짧은 근무를 반복해도 반올림 이익이나 손실이 누적되지 않는다. 퇴근 때 실제 계정 이체가 실패하면 미지급 임금으로 남긴다. 다음 근무 전에 직원이 이를 알려 주고, 새 근무 동의 여부에 반영한다. 체불이 생겼다고 이미 수행한 경험이나 판매를 되돌리지는 않는다.

사장이 자리를 비울 때 보여 주는 요약은 “현재 재고로 처리 가능 / 다음 발주 예상 / 이번 근무 임금” 세 줄이다. 출발을 강제로 막지는 않는다. 직원이 근무 중이면 사장 위치와 무관하게 같은 작업 규칙을 적용한다. 근무가 끝났고 사장도 없으면 계산은 중단되며, 기존 손님의 대기와 이탈 규칙이 작동한다. 무기한 무료 야근으로 가게를 유지하지 않는다.

**14. 마감 보고 한 줄은 실제 사건의 요약이다.** 각 완료 기록에 직원 ID, 작업 ID, 시작·종료 분, 정책 버전, 사장 개입 여부, 사장 부재 구간, 결과 ID를 남긴다. 사장이 작업 전 구간에 부재했고, 건별 승인 없이 정책 안에서 완료했으며, 취소·환불로 뒤집히지 않은 결과만 ‘사장님 없이 해결한 일’ 후보가 된다. 정책을 미리 정한 것은 개입으로 보지 않지만, 해당 발주를 원격 승인한 것은 개입으로 본다.

후보는 예약 인도 완료, 품절 품목 보충 후 실제 판매, 권한 내 흥정 판매, 일반 판매 순으로 고른다. 같은 우선순위에서는 건수가 많은 유형, 같으면 먼저 완료된 기록을 고른다. 예시는 “사장님 없는 동안 예약 두 건을 약속한 수량대로 건넸어요”다. 예약 기록이 없는데 예약 손실을 막았다고 만들지 않는다. 후보가 없으면 “오늘은 함께 근무했어요” 또는 “혼자 처리할 주문은 없었어요”라고 사실대로 쓴다.

**15. 폰에서 위임 완료를 행동으로 느끼게 한다.** 시험 종료 카드에는 처리한 계산·진열과 실제 걸린 시간을 보여 주고 하단에 ‘이 조건으로 채용’을 둔다. 채용 뒤 다섯 정책을 한 화면에서 확인한다. 가게를 떠나면 업무 탭 상단에 ‘근무 중 · 혼자 완료 3건 · 답변 필요 0건’이 표시된다. 정상 거래마다 알림을 울리지 않으며, 긴급 요청만 배지를 붙인다. 마감 보고 한 줄을 누르면 근거가 된 거래 두세 건을 볼 수 있다.

예를 들어 사장은 개발자와 만나러 게임 90분 동안 자리를 비운다. 직원은 예약 물건을 따로 두고 일반 손님 네 명을 계산한다. 우유 보충 18결은 정책 안에서 발주하고, 30결짜리 추가 주문은 승인 요청으로 남긴다. 사장이 답하지 않아도 다른 판매는 계속된다. 돌아왔을 때 실제 매출, 지출, 재고와 직원 보고가 맞아떨어진다. 위임의 보상은 위험 알림을 더 받는 것이 아니라 그 90분을 다른 사업에 쓸 수 있었다는 사실이다.

**마지막: 주제별 Vitest 통과 기준과 시스템 파일 구조**

다음은 구현 후 실행할 기준이다. 화면의 재미와 폰 조작감은 별도 플레이 검증으로 확인한다.

**A의 Vitest 통과 기준 — 8개**

1. **기회와 무자본 진입:** 플레이어 잔액 0에서도 공개 문의·범위 협의가 가능하다. 성공보수 후보와 목록 정리 계약을 체결하면 선금 없이 작업을 시작한다. 기회 노출 조건에 잔액 검사를 넣으면 실패한다.
2. **범위별 결과:** 대표 10건에서 사람 확인 시간이 각각 30·18·6분이다. 모든 범위에서 필수 정보 누락 주문은 자동 확정되지 않는다. 범위 밖 작업은 성공으로 집계되지 않는다.
3. **지급 보존과 원자성:** 일반 계약 180결·개발비 80결의 모든 지급 후 고객 −180, 플레이어 +100, 개발자 +80이다. 선금 없는 계약은 −180·+60·+120이다. 어느 지급이 실패해도 해당 묶음 전체가 변하지 않는다.
4. **검수 재현:** 동일 결과물·시험 입력은 실행 횟수와 저장 재개에 관계없이 같은 결과를 낸다. 반복 검수로 결함이 사라지지 않으며, 안전 사례 하나라도 실패하면 납품 불가다.
5. **재작업과 종료:** 포함 재작업은 한 번이다. 지정한 결함만 수정하고 전체 시험을 다시 실행한다. 미해결 실패는 최종 실패로 남으며 새 계약 없이 진행도·시도 수를 초기화할 수 없다.
6. **데이터와 검토:** 미동의 필드는 개발자 입력에 포함되지 않는다. 반복 상담 결과가 같고 원문은 상담 없이 조회된다. 조항 수정에는 새 버전과 양측 동의가 필요하며 만료된 작업 사본은 제거된다.
7. **미납·환급:** 잔금 부족은 검수 실패로 바뀌지 않는다. 일반 계약 실패 시 환급 32결, 부족분은 채무로 남는다. 반복 지급 명령과 장부 압축 후 재호출에서도 중복 지급이 없다.
8. **시간·운영 연결:** 180분을 한 번에 진행한 결과와 1분씩 진행한 결과가 같다. 개발자 중복 예약이 없고, 다음 일로 넘길 때 직원 급여도 처리된다. 후속 기회에는 실제 운영 기록이 필요하며 자동 수익은 생기지 않는다.

`PaymentObligation`은 지급자·수취자·약정액·지급액·기한·고정 지급 ID를 저장한다. 채무 자체는 돈이 아니다. `AutomationRun`은 입력 기록 ID, 자동 처리 결과, 사람 확인 분을 가진다. 완료 기록은 요약할 수 있지만 지급 중복 방지 ID와 검수 근거는 보존한다.

**B의 Vitest 통과 기준 — 8개**

1. **시험 근무와 채용:** 시험 임금은 정확히 한 번 지급된다. 실제 업무가 없으면 경험·성과를 생성하지 않는다. 채용 여부와 관계없이 수행 경험은 같은 주민에게 남는다.
2. **정책 안 자동 처리:** 사장 부재 중에도 계산·진열·예약 인도·허용 발주가 진행된다. 건당 한도, 하루 예산, 가용액 중 하나라도 부족하면 지급하지 않고 요청한다.
3. **권한 우회 방지:** 주문 쪼개기, 승인 후 가격 변경, 원가 이하 할인, 예약 재고 판매를 막는다. 이전 정책으로 체결한 의무는 새 정책 적용 뒤에도 유지된다.
4. **요청 수명:** 같은 원인의 반복 틱은 메시지를 늘리지 않는다. 한 번 승인한 요청은 한 번만 실행된다. 만료·거절·미응답 중에도 다른 정상 업무는 계속된다.
5. **성장 곡선:** 손 42 직원의 관련 경험 12시간 시 계산 처리량이 기준 사장보다 높다. 유휴·정지 시간에는 경험이 없고, 작업량 이월로 장기 처리량이 공식과 일치한다.
6. **원인 기반 사건:** 같은 시프트·작업·날짜는 같은 난수를 사용한다. 고정 시드 대규모 표본에서 정상 상태의 지각·실수 빈도가 공식의 허용 오차 안에 있고, 과로·통근 장애가 있는 집단보다 낮다. 이직 조건이 없으면 발생 수는 0이다.
7. **정확한 마감 보고:** 보고의 모든 수치가 완료 기록으로 역추적된다. 사장이 승인하거나 중간에 개입한 작업은 ‘혼자 해결’에서 제외된다. 취소된 거래·빈 기록에서 성공 문장을 생성하지 않는다.
8. **돈·시간·장기 실행:** 임금·판매·발주 후 총액이 보존된다. 저장 재개와 틱 분할 결과가 같고, 사장 부재·하루 넘기기에서도 중복 지급이 없다. 주민 지갑과 재고가 고갈되면 판매가 실제로 줄어든다.
